## 1. Objectif et contexte

Nokk_project a été généré initialement par Lovable AI, puis développé en mode « vibe coding » (itération rapide guidée par IA, sans garde-fous de qualité). Un nettoyage du code mort Lovable a déjà eu lieu, mais des traces subsistent, et surtout **aucun mécanisme structurel n'empêche la dette de continuer à s'accumuler** : la CI ne fait tourner ni lint ni typecheck, et les features les plus récentes (CRM, Stock) reproduisent déjà les mêmes anti-patterns (god components, valeurs Tailwind arbitraires) que l'ancien code Lovable. La dette n'est donc pas seulement legacy — elle est **active**.

Ce document répond à une question simple : **comment sortir du vibe coding et garantir une stabilité dans la durée**, sans geler le développement de features.

Deux flux parallèles :
- Un flux **garde-fous** (Phase 0), qui empêche la dette de continuer à croître pendant que le nettoyage a lieu.
- Un flux **nettoyage**, séquencé du risque le plus faible au plus élevé (Phases 1 à 3), exécutable par petites PR isolées et entrelacé avec le développement normal.

## 2. Doctrine parente : ce document n'invente rien

Le projet possède déjà une doctrine d'architecture interne formalisée : **`docs/Architecture_Feature.pdf`** (« Architecture Feature — Guide interne », 11 pages), qui prescrit une architecture **Vertical Slice / Feature-First** avec des règles précises : structure de dossier par feature, hooks `context/data/ui`, couche `services/` obligatoire, seuil god-component à 400 lignes, checklist de revue, plan de migration type, arbre de décision « où je mets ce fichier ? ».

Ce PDF confirme indépendamment une grande partie des constats de cet audit (couche service manquante, appels Supabase directs dans les composants, god components, incohérences de nommage). **Ce document ne réinvente donc pas la doctrine — il l'opérationnalise et comble ses angles morts** : garde-fous CI/lint, gouvernance du design system partagé, sort des pages placeholder, décision crypto, convention env vars.

**Règle de non-duplication** : toute question déjà tranchée par `Architecture_Feature.pdf` (structure d'une feature, conventions de nommage, rôle du context, checklist de revue, anti-patterns, arbre de décision) doit être résolue en s'y référant — pas en recopiant son contenu ici. Ce document se concentre sur ce que le PDF ne couvre pas : le plan d'exécution, les garde-fous techniques, et la gouvernance du design system partagé (voir `docs/DESIGN_SYSTEM.md`).

Un second document complète cette doctrine sur un axe que le PDF ne couvre pas : **`docs/DESIGN_SYSTEM.md`**, qui définit les conventions Atomic Design (atoms/molecules/organisms/templates) pour la couche UI partagée (`src/shared/ui`, `src/shared/components`) — un axe orthogonal à la Vertical Slice, qui reste la doctrine pour l'organisation des `features/*/components`.

## 4. Vue d'ensemble des phases

| Phase | Objectif | Risque | Durée indicative |
|---|---|---|---|
| Phase 0 | Garde-fous structurels + documents de référence dans `/docs` | Très faible | 3–5 jours |
| Phase 1 | Quick wins : fichiers morts, config, code mort confirmé | Faible | 1–2 semaines |
| Phase 2 | Consolidation architecture (data-fetching, service layer, env vars, Tailwind, Atomic Design du design system) | Moyen, scindable en petites PR | 4–8 semaines, en continu |
| Phase 3 | Dette « deux vitesses » restante (god components, couverture de tests) | Élevé pour les god components | Continu, opportuniste |

Phase 0 doit être posée avant tout le reste : c'est elle qui empêche la dette de continuer à croître pendant que les phases suivantes progressent. Phases 2–3 s'entrelacent avec le développement de features normal — migration « boy scout » : on nettoie ce qu'on touche, en suivant le plan de migration type déjà défini dans `Architecture_Feature.pdf` §14.

## 5. Phase 0 — Garde-fous et documents de référence

### 5.1 CI : ajouter les gates manquants — FAIT
**Fichiers** : `ci.yaml`, `scripts/check-quality-ratchet.mjs`, `ci/quality-baseline.json`
- Étape `quality` ajoutée dans `ci.yaml` (juste après `setup`, avant `build`) : lance `npm run check:lint-ratchet` puis `npm run check:typecheck-ratchet`.
- **Mode ratchet** : `ci/quality-baseline.json` contient les compteurs de référence (`lint`: 127 warnings, `typecheck`: 239 erreurs, mesurés à l'introduction du gate). `scripts/check-quality-ratchet.mjs` recompte à chaque run (`eslint . -f json` pour le lint, `oxlint -f json` depuis le 2026-10-20, `tsc --noEmit -p tsconfig.json` pour le typecheck) et échoue seulement si le total dépasse la baseline. La baseline ne doit être abaissée que lorsqu'une réduction réelle du nombre de problèmes est constatée — jamais augmentée pour faire passer une PR sans justification.
- `npm run typecheck` (`tsc --noEmit -p tsconfig.json`) ajouté comme script indépendant, réutilisable en local.

### 5.2 CLAUDE.md à la racine — FAIT
**Fichier** : `CLAUDE.md`. Pointe vers `Architecture_Feature.pdf` et ce document plutôt que de dupliquer leur contenu. Contient les règles non négociables : couche `services/` obligatoire, un seul module crypto autorisé, préfixe env var unique `PUBLIC_*`, interdiction Tailwind arbitraire, scope Atomic Design limité au design system partagé.

### 5.3 Règles ESLint additionnelles — FAIT
**Fichier** : `eslint.config.js`
- `no-restricted-imports` (niveau `warn`, comptabilisé par le ratchet §5.1) : interdit l'import direct de `@/integrations/supabase/client` en dehors de `**/services/**`.
- `no-restricted-imports` : interdit `@radix-ui/react-*` en dehors de `src/shared/ui/**`.
- Interdit les imports vers les chemins morts de `components.json` (`@/components/*`, `@/lib/*`, `@/hooks/*`).
- Implémenté via des blocs `files:` par zone (règle générale + exception `**/services/**` + exception `src/shared/ui/**`) pour que les exceptions légitimes ne remontent pas de warning.
- Mesuré à l'introduction : 127 warnings existants (essentiellement des imports Supabase directs déjà recensés dans l'audit), aucune erreur bloquante — cohérent avec le mode ratchet.

### 5.4 Structure de dossier imposée pour les nouvelles features
Déjà documentée dans `Architecture_Feature.pdf` §2 — rien à réinventer. `CLAUDE.md` y renvoie et cite `src/features/stock/` comme exemple le plus proche de la cible actuelle.

### 5.5 Ce document (`docs/PLAN_ASSAINISSEMENT.md`) — FAIT
Livrable en lui-même — voir §10 pour le tableau de suivi qui en fait un document vivant plutôt qu'un instantané figé.

### 5.6 `docs/DESIGN_SYSTEM.md` — FAIT
Conventions Atomic Design pour `src/shared/ui` + `src/shared/components`, avec inventaire de classification proposé pour les fichiers existants. Voir document séparé.

**Phase 0 complète.** Reste ouvert : la validation humaine des décisions §9 (suppression des pages placeholder, mode ratchet vs strict — déjà appliqué en ratchet par défaut) avant de lancer la Phase 1.

## 7. Phase 2 — Consolidation architecture (continue, en parallèle des features)

### 7.1 Data-fetching : exploiter React Query, ne pas le supprimer
`QueryClientProvider` déjà actif (`src/app/providers/AppProviders.tsx`) mais 0 `useQuery`/`useMutation` dans tout le repo, contre 139 fichiers en fetch direct/`useEffect` et 126 imports Supabase directs. Convention imposée par le gate ESLint (§5.3) pour tout nouveau code, alignée sur `Architecture_Feature.pdf` §5 : composant → hook `hooks/data/use<Ressource>()` → `services/<ressource>Service.ts`. Migration de l'existant en mode « boy scout », pas de big-bang.

### 7.2 Généraliser la couche service
Étendre le pattern `services/` (modèle `arrivageService.ts`) à CRM, Messages, Tickets, Projects, en suivant le plan de migration type déjà écrit dans `Architecture_Feature.pdf` §14.

**Messages : première extraction FAITE** (2026-07, hors séquence des phases — demandée explicitement après la clôture de la Phase 3). Périmètre volontairement restreint pour une première passe sur une feature crypto-sensible :
- `src/features/messages/services/` créé avec 5 fichiers : `keyBundleService.ts` et `userKeysService.ts` (relocalisés depuis `core/bundle.ts`/`core/sync.ts` — déjà des fonctions pures, juste déplacées + import paths corrigés), `profilesService.ts` et `conversationsService.ts` (nouveaux, extraits des requêtes `supabase.from()` inline de `useCryptedUsers.ts`/`useRecentConversations.ts`).

Extraction ciblée uniquement de ces 2 appels vers `deleteRemoteBundle()`/`deleteRemoteUserKeys()` (comportement strictement identique, mêmes table/filtre/opération) — **le reste du fichier n'a pas été touché**, pas de refactor plus large de ce god component sans revue métier.

### 7.8 Theming : sweep des couleurs codées en dur — FAIT (2026-08-12)

Résorption des 459 warnings `no-restricted-syntax` restants (baseline lint **459 → 0**). Principe retenu : tokeniser quand l'équivalence visuelle est stricte, poser une exception ESLint commentée uniquement pour les cas que `DESIGN_SYSTEM.md` §12.4 autorise déjà — jamais pour faire taire la règle sur de la vraie dette.

**Tokenisé** (~330 occurrences) :
- `bg-white[/alpha]` → `bg-card[/alpha]` : `--card` vaut blanc pur en thème clair, donc iso ; quand un `dark:bg-*` explicite existait il continue de primer, et là où il manquait la surface suit désormais le thème sombre au lieu de rester blanche.
- `dark:text-white` → `dark:text-foreground`, et `text-white` → `text-<role>-foreground` **uniquement** quand un aplat sémantique (`bg-primary`, `bg-success`, `bg-destructive`…) était présent dans la même déclaration de classes — ces tokens valent blanc pur dans `:root` comme dans `.dark`.
- Boutons et badges colorés bruts (`bg-green-600`, `bg-red-500`, `bg-slate-900`…) → tokens sémantiques (`bg-success`, `bg-destructive`, `bg-foreground`…). Les teintes bougent légèrement : c'est le but de la règle.
- Grilles, axes et points Recharts (`stroke="#e5e7eb"`, `"#9ca3af"`, `fill="#fff"`) → `hsl(var(--border))` / `hsl(var(--muted-foreground))` / `hsl(var(--card))`.
- Palettes de séries → `CHART_PALETTE` (`src/shared/lib/chartPalette.ts`) ou `hsl(var(--chart-N))` : Matomo, sell-journal, tickets, leads, tunnel de vente CRM, `crm/utils/eventTypes.ts`, `projects/project_constants.ts` (`MEMBER_COLOR_PALETTE` n'est plus qu'un alias de `CHART_PALETTE`).

- Faux positif : `shared/ui/organisms/chart.tsx`, où `#ccc`/`#fff` sont des *sélecteurs* ciblant les valeurs par défaut de Recharts pour les remplacer par des tokens.
