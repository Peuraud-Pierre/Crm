# Courbe de tendance « Produits recherchés » — CRM Analytics

Date : 2026-09-03
Feature : `src/features/crm`

## Contexte

`AnalyticsTab.tsx` affiche déjà plusieurs widgets (CA, RDV, provenance...) calculés
à la volée à partir des clients chargés en mémoire (`AnalyticsContext.tsx`). Le
brief client (`client_crm.brief`, colonne JSONB, typé `FicheAppro` côté front)
contient un tableau `recherche: Recherche[]` — les « Produits recherchés »
saisis sur la fiche client (section « Produits Recherchés » de
`colonneBrief.tsx`). Ces entrées n'ont pas de date propre (juste
`{ nom, quantite, prix? }`).

Le besoin : une courbe de tendance mensuelle du nombre total d'entrées
`recherche` sur l'ensemble des briefs, affichée dans `AnalyticsTab.tsx`. Comme
les entrées n'ont pas de date individuelle, on ne peut pas reconstituer
l'historique après coup — la seule option est une **photo mensuelle** de
l'état courant, enregistrée en base chaque mois, pour accumuler l'historique
au fil du temps.

## Décisions validées

- **Métrique** : total d'entrées dans `brief.recherche[]`, sommé sur tous les
  `client_crm`, à l'instant du snapshot (pas le nombre de clients distincts).
- **Déclenchement** : automatique côté DB via `pg_cron`, 1 fois par mois. Pas
  de dépendance à l'ouverture de l'app.
- **Pas d'historique rétroactif** : le premier point de la courbe est le mois
  du déploiement (backfillé une fois par la migration), pas avant.

## 1. Table `crm_produit_recherche_stats`

```sql
CREATE TABLE public.crm_produit_recherche_stats (
    id             bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    snapshot_month date NOT NULL UNIQUE,   -- toujours le 1er du mois (date_trunc('month', ...))
    total_entries  integer NOT NULL,       -- somme des jsonb_array_length(brief->'recherche')
    created_at     timestamptz NOT NULL DEFAULT now()
);
```

- Une ligne par mois (`snapshot_month` unique) — le job fait un upsert, donc un
  re-run manuel dans le mois écrase la valeur au lieu de dupliquer.
- Pas de colonne par produit / catégorie : hors scope (YAGNI — la demande est
  un total, pas une ventilation).

## 2. Fonction de snapshot + planification `pg_cron`

Fonction `public.snapshot_produit_recherche_stats()` (`SECURITY DEFINER`,
comme les autres jobs cron du repo) :

- Parcourt `public.client_crm.brief`, gère le cas où `brief` est stocké comme
  chaîne JSON encodée (cas déjà connu côté TS : `Client.brief?: FicheAppro |
  string | null`) via un `CASE jsonb_typeof(brief) = 'string' THEN
  (brief#>>'{}')::jsonb ELSE brief END`.
- Somme `jsonb_array_length(brief_json->'recherche')` pour les briefs où ce
  champ est bien un array (`jsonb_typeof(...) = 'array'`), en ignorant les
  briefs `NULL` ou malformés (pas d'erreur bloquante sur une ligne corrompue).
- `INSERT ... ON CONFLICT (snapshot_month) DO UPDATE` sur
  `date_trunc('month', now())::date`.

Planification, suivant exactement le pattern de
`20260707150000_arrivage_invoice_reminder_cron.sql` (guard
`pg_available_extensions` / `pg_extension`, `cron.unschedule` puis
`cron.schedule`) :

- Nom du job : `crm-produit-recherche-monthly-snapshot`.
- Cron : `0 2 1 * *` (1er de chaque mois, 02:00 UTC).

La migration appelle aussi `SELECT
public.snapshot_produit_recherche_stats();` une fois à la fin, pour que le
mois courant apparaisse immédiatement dans la courbe sans attendre le
prochain 1er du mois.

## 3. RLS

- `ENABLE ROW LEVEL SECURITY`.
- Une seule policy `SELECT`, gatée sur la permission `crm.view` (même modèle
  que `brief_cat`, cf. `20260813120000_crm_brief_options.sql`) :
  ```sql
  CREATE POLICY "crm.view can read produit recherche stats"
      ON public.crm_produit_recherche_stats FOR SELECT
      TO authenticated
      USING (public.user_has_permission(auth.uid(), 'crm.view'));
  ```
- Pas de policy `INSERT`/`UPDATE`/`DELETE` pour les rôles applicatifs : seule
  la fonction `SECURITY DEFINER` (exécutée par le cron, donc par le rôle
  Postgres propriétaire) écrit dans la table.

## 4. Couche service + hook (obligatoire, `CLAUDE.md`)

`src/features/crm/services/produitRechercheStatsService.ts` — même pattern que
`briefOptionsService.ts` : client Supabase casté (`as unknown as
SupabaseClient`) tant que la table n'est pas dans `integrations/supabase/types.ts`
(généré), avec le commentaire de régénération standard.

```ts
export interface ProduitRechercheStatPoint {
    month: string   // "2026-09-01"
    total: number
}

export async function listProduitRechercheStats(): Promise<ProduitRechercheStatPoint[]>
```

`src/features/crm/hooks/data/useProduitRechercheStats.ts` — hook de
chargement (fetch au montage, état `{ data, isLoading, error }`), suivant le
style des hooks `hooks/data/` déjà en place ailleurs dans le repo (référence
stock). Pas de dépendance à `AnalyticsContext` : cette donnée n'a pas besoin
d'être filtrée par période/collaborateur comme le reste des KPIs (c'est un
total global déjà agrégé côté DB), donc un hook autonome consommé directement
par le nouveau widget est plus simple qu'une intégration dans le contexte.

## 5. Widget UI

`src/features/crm/components/Analytics/Widget/ProduitsRecherches.tsx` :

- Suit le template `Widget/Provenance.tsx` : `Card` (`@/shared/ui/atoms/card`),
  header icône + titre + sous-titre muted, `ResponsiveContainer` h-300,
  `RECHARTS_TOOLTIP_THEME` (`@/shared/lib/rechartsTooltip`), état vide
  (« Aucune donnée pour cette période »), `motion.div` `AnimatePresence`
  cohérent avec `Charts.tsx`.
- `LineChart` Recharts (courbe, pas des barres — c'est une tendance dans le
  temps), un seul `Line` (total mensuel), axe X = mois formaté (`MMM yyyy`
  via `date-fns/locale/fr` si déjà utilisé ailleurs dans le repo, sinon
  formatage manuel cohérent avec les autres widgets d'évolution).
- Nouveau `WidgetId` (ex. `"produits-recherches"`) ajouté dans
  `src/features/crm/types/stats.ts` (`DEFAULT_WIDGET_CONFIG`), et branché
  dans `Charts.tsx` au même niveau que les autres widgets d'évolution
  (`revenueEvolutionData`, `rdvEvolutionData`...).

## Hors scope

- Ventilation par produit/catégorie (juste un total).
- Export Excel de cette courbe (`ExportStatsButton.tsx` reste inchangé — pas
  de lien avec ces données).
- Reconstruction d'un historique antérieur au déploiement (impossible, pas de
  date par entrée `recherche`).
- Régénération de `src/integrations/supabase/types.ts` : à faire manuellement
  après application de la migration (commande documentée dans le commentaire
  du service, comme pour `briefOptionsService.ts`).
